# Lit-Review 020: Substrate-and-Surface Separation for Methodology Documentation

*Date:* 2026-05-22

---

## Synthesis

The literature converges on a recognizable pattern: multi-resolution viewing is empirically validated as beneficial when the navigation structure preserves context across abstraction levels, but it carries documented failure modes (context loss at zoom boundaries, cognitive cost of re-orienting between levels, dual-maintenance staleness) that are not merely implementation defects but structural properties of any two-layer architecture. For the specific consumption pattern RDD exhibits — a corpus that agents read in full and humans read selectively — the substrate question resolves into a choice between a persisted structured representation (graph or linked-record) and an agent-emergent-in-context approach (agent constructs the graph on demand from plain-text sources). The empirical literature on graph-augmented LLM agents (GraphReader; Kantara; Architecture Knowledge Graphs 2024) supports the former for retrieval accuracy and provenance preservation at scale; the practical literature on plugin-native implementations (YAML frontmatter as virtual graph; JSON-LD as lightweight linked data; docs-as-code) supports the latter for zero-dependency deployment. The documentation read-rate literature (Lethbridge, Singer, Forward 2003; Garousi & Garousi 2013; 2014) confirms that decision-rationale and design documentation are among the least-consulted artifact types post-build, with usage concentrated in active development phases — providing empirical grounding for the practitioner's "no one reads them post-graduation" observation. The specific intersection of (a) methodology documentation corpora, (b) solo-developer context, (c) LLM agent as primary consumer, and (d) human practitioner as secondary consumer has no direct empirical literature; findings below are directional convergences across adjacent literatures, scoped accordingly.

## Six Research Questions and Findings

### Q1: Substrate Forms for Separating Overview from Detail in Software Documentation

**Finding 1.1 — Literate programming (Knuth 1984)**

Knuth's literate programming model generates two representations from a single source: "tangled" code for compiler consumption and "woven" documentation for human reading. The structural contribution is the single-source-of-truth discipline: documentation and implementation derive from the same artifact, eliminating the divergence problem. The limitation for RDD's use case is directionality: the two outputs are targeted at distinct fixed audiences (compiler vs. human reader) rather than at multiple human resolution levels or at an agent+human split. Audit-substance is preserved in the source; the woven form can lose detail depending on the weaving configuration. CONFIDENCE: Established literature. IMPLICATION: The single-source discipline is the applicable carry-forward. The dual-output pattern is a relevant structural precedent even though its specific audience split does not match RDD's.

**Finding 1.2 — C4 model (Brown, 2006–2011)**

The C4 model provides four abstraction levels for software architecture documentation — Context, Container, Component, Code — each targeting a different audience and level of detail. It is explicitly designed for multi-resolution communication: the same system is described at Level 1 for non-technical stakeholders and at Level 4 for developers working in the code. Structurizr (Brown's accompanying tooling) enables "models as code" — version-controlled, plain-text-compatible diagram source that generates multiple views from a single model. Audit-substance: preserved at the model layer; surface views are computed, not independently maintained. Plugin-native: the underlying model is text (DSL); Mermaid and Graphviz can consume outputs. CONFIDENCE: Established practice, widely adopted. Empirical evaluation of the model as a documentation form for decision records specifically is sparse. IMPLICATION: The C4 pattern is the closest existing architectural analog to the practitioner's hypothesis. It demonstrates the viability of single-model → multi-resolution-view architecture in a plain-text-compatible substrate. The limitation is that C4 diagrams capture structural decomposition, not decision rationale or invariant networks — the specific content RDD's substrate must carry.

**Finding 1.3 — arc42 template (Starke & Hruschka, 2005)**

arc42 provides a 12-section framework covering context, quality requirements, building blocks, runtime behavior, deployment, and cross-cutting concepts. It explicitly supports multi-level granularity through hierarchical building-block decomposition (white boxes containing black boxes). It is tool-agnostic (Markdown, AsciiDoc, wiki). The practitioner-facing literature notes two failure modes: (a) it can be overwhelming for simple systems, where the template's comprehensiveness defeats the documentation goal; (b) it was designed for deterministic software and cannot capture probabilistic or data-dependent behavior without extension. Audit-substance: high, when populated. Plugin-native: yes, Markdown-compatible. CONFIDENCE: Established practice. IMPLICATION: arc42's building-block decomposition pattern (hierarchical, level-selectable) is relevant structural precedent. Its failure mode (comprehensiveness → overwhelm) is exactly the user-reported fatigue pattern and worth attending to as a negative case.

**Finding 1.4 — ADR as code / architecture comment systems (Nygard 2011; Keeling; Fairbanks)**

The ADR format (Nygard 2011; popularized by Keeling at IBM Watson) is a lightweight, markdown-native record of individual architectural decisions with structured fields (Context, Decision, Consequences, Alternatives). Its structural property is atomicity: one decision per record. The IBM Watson corpus (>80 ADRs across cloud microservices) is the best-documented practitioner application of ADR-at-scale. Keeling's guidance distinguishes decisions warranting an ADR (quality attribute impact, technical debt introduction, structural change, hard-to-reverse) from those that do not. No ADR-native tooling provides multi-resolution overview; navigation across an ADR corpus requires either tooling (adr-tools, log4ADR) or agent-assisted traversal. Audit-substance: high per-record; cross-record summary and topology are not provided by the format itself. CONFIDENCE: Established practice, directional empirical evidence from field reports. IMPLICATION: The ADR format's atomicity is both its strength (audit-substance per record is preserved) and the source of the topology problem RDD names (no native overview; reader must construct topology). The format's weaknesses map directly to the cycle's problem statement.

**Finding 1.5 — Fitness functions / evolutionary architectures (Ford, Parsons, Kua, Sadalage, *Building Evolutionary Architectures*)**

Fitness functions are "any mechanism that provides an objective integrity assessment of some architectural characteristic." They serve as executable architecture documentation — the architecture's decisions are encoded as tests that run continuously and fail if violated. For audit-substance: very high for the architectural properties they test; zero for decision rationale (the *why* behind the fitness function is external to it). For multi-resolution: fitness functions collapse the overview/detail distinction by making architectural intent machine-verifiable rather than human-readable. CONFIDENCE: Established practice. IMPLICATION: Fitness functions are audit-substance-preserving for behavioral properties and are the strongest existing mechanism for preventing architecture-code drift. They do not address the human-readable overview problem and require code-level implementation, making them unsuitable as a standalone substrate for RDD's purpose. They are a complementary form, not a substrate candidate.

**Finding 1.6 — Spec-by-example / living documentation (Adzic 2011)**

Adzic's specification-by-example methodology produces living documentation as a byproduct of acceptance testing: executable specifications that both document behavior and validate it. The audit-substance is high (behavior is both documented and tested); the surface is human-readable (plain-language scenario + outcome). The failure mode at architectural scale is the same as scenarios-only in RDD: fine-grained scenarios do not provide big-picture overview, and the corpus weight grows with coverage. CONFIDENCE: Established practice, empirically studied. IMPLICATION: Living documentation solves the documentation-drift problem (the spec and the test are the same thing) but does not solve the overview problem. This is consistent with the practitioner's rejection of "decisions-as-scenarios-only" in Step 1.4 of the research log.

### Q2: Multi-Resolution Information Presentation

**Finding 2.1 — Shneiderman's visual information-seeking mantra (1996)**

Shneiderman (1996) articulated the foundational three-stage pattern: "overview first, zoom and filter, then details on demand." The mantra has become the standard reference for multi-resolution information interface design and appears as a design goal in virtually all subsequent hierarchical visualization work. Its empirical grounding is in direct-manipulation interfaces (treemaps, starfields, dynamic queries) rather than document corpora; the applicability to documentation navigation is analogical rather than directly empirical. CONFIDENCE: Foundational established reference. IMPLICATION: The practitioner's named preference ("high-level picture that leads to sub-system pictures") is structurally equivalent to Shneiderman's mantra. The research log's citation of Shneiderman is appropriate. The gap is empirical evidence that the mantra applies to documentation corpus navigation specifically, which is not directly addressed.

**Finding 2.2 — Cockburn, Karlson, Bederson (2008): Review of overview+detail, zooming, and focus+context interfaces**

This ACM Computing Surveys review categorizes multi-resolution interfaces into four families: overview+detail (spatial separation of context and focus views), zooming (temporal separation), focus+context (focus displayed within context), and cue-based (selective highlighting). The empirical evidence reviewed is mixed: overview+detail designs consistently show user preference and lower subjective task load, but zooming interfaces often produce faster task completion (contrary to design intuitions). The paper identifies specific failure modes: (a) **split-attention cost** — when overview and detail are spatially separated, users bear cognitive cost keeping them linked; (b) **context loss at zoom boundary** — users navigating via zoom lose the overview frame of reference; (c) **no universal winner** — which family is best depends on task structure, specifically whether context must be consulted simultaneously with detail or can be consulted in sequence. CONFIDENCE: Empirically established for HCI interface tasks; no direct transfer to documentation corpus navigation established. IMPLICATION: The split-attention cost is directly relevant to RDD. If the substrate layer (agent-facing) and the surface layer (human-facing) are maintained separately, users bear a split-attention cost when the two diverge or when navigating between them. The task-structure dependency finding suggests the right architecture depends on whether practitioners need to consult overview and detail simultaneously (during gate decisions) or sequentially.

**Finding 2.3 — Tversky: Cognitive maps, cognitive collages, and spatial mental models (1993)**

Tversky (1993) established that mental representations of spatial environments are hierarchically organized but imprecise and schematic — "cognitive collages" assembled from disparate sources rather than accurate maps. Distortions arise from cognitive organizing principles: hierarchical organization, reference points, perspective-taking. The findings imply that practitioners' mental models of a corpus will be hierarchically organized (coarse → fine) but will contain systematic distortions at hierarchy boundaries. For documentation design: overviews should be designed for the coarse level practitioners actually form, not for the level at which details are most accurate. CONFIDENCE: Established cognitive science literature. Applicability to software documentation corpus navigation is analogical. IMPLICATION: The practitioner's felt preference for a "picture that is easier to reason about" at the high level is consistent with Tversky's finding that coarse hierarchical representations are how people actually hold spatial (and, analogically, structural) information. The implication for substrate design is that the user-facing surface should match the resolution at which practitioners naturally think about the corpus, not the resolution at which decisions were made.

**Finding 2.4 — Card, Mackinlay, Shneiderman (1999): Readings in Information Visualization**

The foundational anthology defines information visualization as "the use of interactive visual representations of abstract data to amplify cognition." The reference model (IVRM) describes the data → transformation → visual → view pipeline. For documentation: the substrate is the data layer; the surface is the view layer; the transformation is the rendering step (Mermaid generation, Graphviz, agent-generated ASCII, computed summaries). The anthology establishes the pipeline as a design principle: view and data are separable, and multiple views can be generated from the same data without modifying the data. CONFIDENCE: Foundational established reference. IMPLICATION: The view-pipeline model directly supports the practitioner's hypothesis (substrate as data layer; surface as view layer). It implies the substrate must be structured enough to support the transformation step reliably.

**Finding 2.5 — Zooming vs. multiple-window interfaces: cognitive costs (Cockburn & McKenzie 2002)**

In a controlled study, Cockburn and McKenzie (2002) compared zoom-to-details versus multiple-window interfaces for navigation tasks and found that **zooming generates extra cognitive load** for users linking pre-and post-zoom states. The study is one of the few direct empirical comparisons of zoom approaches for document navigation. CONFIDENCE: Empirically established in a specific navigation task context; generalization to corpus navigation is directional. IMPLICATION: For RDD, if the "zoom to detail" is implemented as a drill-in to a full ADR from a high-level view, the cognitive cost of linking the two states is a real design cost, not negligible. The preferred implementation would maintain context (focus+context family) rather than replace context (zooming family).

### Q3: Knowledge Graphs for Software Design Intent

**Finding 3.1 — Architecture Knowledge Graphs: A Next Step in Architecture Knowledge Management (de Boer, VU Amsterdam, 2024)**

This ACM SATrends 2024 paper argues that linked-data principles applied to software architecture documentation constitute the next step in architecture knowledge management, beyond semantic wikis. The approach constructs an Architecture Knowledge Graph (AKG) from architecture decisions and model elements, enabling connection of knowledge across organizational boundaries. The substrate is RDF-based (linked data principles), which provides provenance and traceability. The paper observes that semantic wikis have helped organize semi-structured knowledge but do not enable the cross-repository linking that an AKG provides. Dependencies: RDF tooling or semantic wiki infrastructure. Plugin-native concern: not directly addressed; the paper targets enterprise architecture contexts with dedicated tooling. Scale evidence: applied to Dutch public sector reference architectures; corpus size comparable to RDD's (~100 ADRs scale) appears tractable. CONFIDENCE: Directional — single practitioner-domain application, no controlled comparison with alternatives. IMPLICATION: This is the most directly relevant academic work to the practitioner's graph-substrate hypothesis. It validates the direction (linked-data-backed architecture knowledge graph) in a comparable corpus-size context, but with heavier dependencies than RDD's plugin-native constraint allows.

**Finding 3.2 — Kantara: End-to-End Rationale Reconstruction (arXiv:2209.00398, 2022; arXiv:2311.03358, 2023)**

Kantara is an NLP-ML pipeline that extracts design decisions and rationale from commit messages and produces an ontologically-based knowledge graph of decision and rationale nodes. It provides provenance tracing of decision evolution over time. Preliminary evaluation on Linux Kernel commit history shows extractable decision structure. Dependencies: requires ML/NLP inference pipeline to construct the graph; not plain-text-native. The KG output is queryable and can generate analysis reports and visualizations. Audit-substance: preserved in the extracted graph. CONFIDENCE: Early-stage research (pilot evaluation). IMPLICATION: Kantara's approach is the automated-extraction variant of the practitioner's hypothesis — rather than building the graph by hand or through structured authoring, the graph emerges from existing artifacts. The dependency profile (ML pipeline) disqualifies it for plugin-native deployment, but the structural goal (graph of decision nodes with rationale and provenance) is the same.

**Finding 3.3 — GraphReader: Graph-based agent for long-context LLM tasks (arXiv:2406.14550, 2024, EMNLP 2024 Findings)**

GraphReader builds a graph structure from long-form text documents and deploys an agent that performs coarse-to-fine graph traversal to answer questions. Using a 4k context window, it consistently outperforms GPT-4-128k on long-context tasks (16k–256k token documents). The graph is constructed from the text, not authored separately — this is the agent-emergent-in-context approach. The agent invokes predefined functions to read node content and neighbors, recording insights and reflecting throughout traversal. Audit-substance: high — the graph preserves provenance links to source documents. Dependency profile: the graph construction pipeline requires an index-building pass; query-time traversal is self-contained. CONFIDENCE: Empirically established (EMNLP 2024 peer review, controlled benchmarks). IMPLICATION: This is the strongest empirical result bearing on the agent-emergent approach. It demonstrates that graph-structured navigation outperforms direct long-context consumption for complex corpus tasks — directly relevant to an RDD corpus of ~100 ADRs. The on-demand construction approach (agent builds graph at query time) is more plugin-native than a persisted KG.

**Finding 3.4 — AGENTiGraph: Multi-agent knowledge graph framework (arXiv:2508.02999, 2025)**

AGENTiGraph unites LLM capabilities with multi-agent processes for end-to-end KG management, including intent classification, graph updates, and knowledge integration. The system targets interactive domain-specific chatbots. Dependency profile: requires LangChain/LangGraph infrastructure and a graph store. Not plugin-native. CONFIDENCE: Directional — single system description, limited comparative evaluation. IMPLICATION: Represents the current state-of-the-art in agent + KG integration but requires heavier infrastructure than RDD's constraint permits. Confirms the direction is actively developed.

**Finding 3.5 — Structured Linked Data as a Memory Layer for Agent-Orchestrated Retrieval (Volpini et al., arXiv:2603.10700, 2026)**

This controlled experiment compares three document representations — plain HTML, HTML with JSON-LD markup, and enhanced agent-optimized entity pages — for retrieval accuracy across four domains. Results: JSON-LD alone provides modest improvement over plain HTML; enhanced entity pages with llms.txt-style agent instructions, breadcrumbs, and navigational affordances achieve +29.6% accuracy improvement for standard RAG and +29.8% for agentic multi-hop traversal. The incremental gain from Enhanced+ over the base enhanced format is not statistically significant, suggesting diminishing returns from additional navigational complexity. Plugin-native concern: JSON-LD can be embedded in plain files with no external database dependency; the enhanced entity-page pattern requires structured authoring conventions. CONFIDENCE: Empirically established in a controlled experiment (four domains, multiple conditions). IMPLICATION: JSON-LD as a substrate layer shows modest gains over plain text; the larger gains come from navigation affordances (breadcrumbs, agent instructions). This supports the practitioner's hypothesis that structured substrate outperforms flat text for agent navigation, but suggests the gain mechanism is navigational scaffolding more than schema richness per se. This is the most directly applicable empirical result for the plugin-native constraint.

### Q4: Plain-Text Structured-Data Alternatives to Graph

**Finding 4.1 — YAML frontmatter as virtual graph**

The emerging pattern in agent-tooling literature (multiple practitioner sources, 2024–2026) treats YAML frontmatter cross-references as a "virtual knowledge graph that exists purely in the file structure." The agent reads frontmatter (50–100 tokens per file) to build an index of available capabilities, then loads full document bodies only when needed. Tools like Obsidian's link parser and similar systems parse vaults into untyped graphs where every Markdown file is a node and every wiki-link is an edge. The approach is fully plugin-native (pure Markdown + YAML), zero-dependency, and version-controllable via git. Audit-substance: preserved in the body; the frontmatter carries metadata and cross-references. Limitation: the graph is implicit (the agent must infer topology from link traversal) rather than explicit (no typed edge metadata, no queryable graph API). CONFIDENCE: Directional — widely adopted pattern, no controlled empirical comparison with explicit graph representations. IMPLICATION: YAML frontmatter with cross-references is the most plugin-native candidate and the easiest to implement in an existing Markdown corpus. The limitation (implicit graph, no typed edges) matters for provenance queries that require reasoning about relationship type (e.g., "which ADRs supersede which; which invariants constrain which decisions").

**Finding 4.2 — JSON-LD as lightweight linked data in JSON**

JSON-LD (W3C standard) encodes linked-data semantics in plain JSON, mapping JSON object properties to concepts in an ontology via a context document. It is designed to express every major web-based structured data model and to be processable by any JSON-capable system. The provenance standard (W3C PROV-O) maps cleanly onto JSON-LD, enabling explicit provenance representation. Plugin-native: files are plain JSON, parseable by any agent without external database. The "Follow Your Nose" principle (resolvable IRIs enable link traversal) allows agents to discover related documents without a central index. Audit-substance: high — typed relationships, provenance links, historical evolution all expressible. Limitation: requires disciplined authoring conventions (contexts must be defined and maintained); human readability of the raw JSON-LD is lower than Markdown frontmatter. CONFIDENCE: Established standard; Volpini et al. 2026 provides the most directly relevant empirical test (Finding 3.5). IMPLICATION: JSON-LD is a middle path between YAML frontmatter (fully implicit) and a graph database (requires external infrastructure). It is the strongest plugin-native candidate that preserves typed-edge provenance semantics.

**Finding 4.3 — Agent-emergent-in-context graph construction**

The GraphReader pattern (Finding 3.3) and related work (Graph of Agents, arXiv:2509.21848, 2025) demonstrate that agents can construct graph structures on demand from plain-text corpora without a persisted graph store. The graph is constructed at query time, used for traversal, and not persisted between sessions (or can be persisted as a cache). For RDD's corpus (~100 ADRs, ~500KB): this corpus is small enough that on-demand construction per session is feasible without index pre-building. Audit-substance: derived from the source documents; the graph reflects the documents' content at construction time. Limitation: the graph may reflect the agent's parsing decisions, not the authors' intent — provenance of typed relationships is implicit rather than explicit. CONFIDENCE: Empirically established for retrieval tasks (GraphReader, EMNLP 2024); applied to methodology corpora is directional extrapolation. IMPLICATION: Agent-emergent construction is the fully plugin-native approach — it requires no structured authoring beyond the existing Markdown corpus. The limitation is that it shifts the topology question from "authors declare relationships" to "agent infers relationships," which may produce inconsistent graph topology across sessions.

**Finding 4.4 — JSON linked-list as structured-record chain**

The practitioner's candidate — "a JSON linked-list" — maps structurally to a chained-record pattern: each ADR record contains explicit links to its predecessors and successors, creating a traversable linked list. This is a simplification of JSON-LD (typed links, no ontology required) and a strengthening of YAML frontmatter (explicit link semantics rather than implicit wiki-link parsing). No direct literature addresses this specific form, but it is consistent with the structured-record patterns in scenarios.md-style blocks (RDD's existing scenario format) and with the structured-block patterns in agent-tooling literature. Audit-substance: depends on implementation — if each record carries full decision content + typed links, audit-substance is preserved. Plugin-native: yes, plain JSON. CONFIDENCE: No direct empirical literature. The form is structurally sound by analogy to adjacent patterns. IMPLICATION: The JSON linked-list is a feasible plugin-native candidate. The critical design question is the typed-link schema: what relationship types must the structure express to support both agent navigation and human-facing surface generation?

**Finding 4.5 — Structured-block patterns (scenarios.md-style)**

RDD's existing scenarios format demonstrates structured-block plain-text records (Given/When/Then + metadata). This pattern is agent-navigable, human-readable, and audit-substance-preserving. Extending this pattern to ADRs (with explicit typed cross-reference fields) is a zero-dependency approach. Limitation: the flat list structure does not provide the hierarchical/graph topology the practitioner identified as the goal; linked lists and cross-reference fields are needed to reconstruct topology. CONFIDENCE: In-corpus pattern (RDD's own existing practice). No external empirical study. IMPLICATION: The structured-block extension is the lowest-risk starting point for a spike — it extends an already-validated pattern in the corpus rather than introducing a new one.

### Q5: Negative Cases — Where Dual-View and Substrate-and-Surface Separation Has Failed

**Finding 5.1 — Dual-maintenance staleness (documentation drift)**

The documentation literature consistently identifies dual-maintenance as a primary failure mode for any two-layer system. When the overview/summary layer and the detail layer are maintained independently, they diverge over time. Research on documentation staleness confirms this: software documentation artifacts are frequently found to be "outdated, incomplete and sometimes not beneficial" (Garousi & Garousi 2014). In the dual-view pattern specifically: if the human-facing surface is computed from the substrate, divergence is prevented at the cost of computation overhead. If the surface is independently authored, divergence is guaranteed over a long-enough time horizon. CONFIDENCE: Empirically established pattern across multiple studies. IMPLICATION: Single-source-of-truth (substrate → computed surface) is the only proven mitigation for dual-maintenance staleness. Independently maintained overview and detail layers will diverge. This is a hard constraint on the architecture.

**Finding 5.2 — Over-confidence in incomplete overviews (Cockburn et al. 2008)**

Cockburn et al.'s review documents a recurrent failure mode in overview+detail interfaces: users develop over-confidence in the overview's completeness and fail to consult the detail layer for exceptions and edge cases. In documentation systems, this maps to practitioners reading the high-level ADR summary and assuming it captures the full decision content, when the detail substrate contains caveats, rejected alternatives, and graduation triggers that are consequential. CONFIDENCE: Empirically established in HCI interface contexts; analogical applicability to documentation systems is directional. IMPLICATION: The user-facing surface must be designed to signal its own incompleteness — specifically, to make it evident when the substrate contains consequential content that the surface does not show. This is a design requirement for the surface layer, not a disqualification of the two-layer approach.

**Finding 5.3 — arc42/C4 comprehensiveness failures**

Practitioner literature on arc42 and C4 documents a consistent failure mode: templates designed for comprehensive coverage tend to produce documentation that is too heavy for simple systems and too light (template-driven rather than decision-driven) for complex systems. The C4 model "felt very comprehensive, but by being comprehensive, it failed to represent the salient points." The arc42 template "can be overkill for simple systems." Both systems fail when the documentation structure is driven by template slots rather than by actual decisions made. CONFIDENCE: Directional — practitioner reports, not controlled studies. IMPLICATION: A substrate-and-surface architecture must be decision-driven, not template-driven. Empty slots in a template are a failure mode, not a neutral placeholder. This maps to the Calibration-with-Graduation-Trigger Pattern finding in Loop 1: substrate entries should appear when decisions are made, not as pre-populated template slots.

**Finding 5.4 — Parnas information hiding: misapplied abstraction**

Brooks (1975, *Mythical Man-Month*) initially rejected Parnas's information-hiding principle as "a recipe for disaster" before reversing his position in the 1995 anniversary edition ("Parnas was right, and I was wrong"). The episode is historically relevant as a case where the critique of abstraction was itself wrong — but the reversal took 20 years. For RDD: the parallel critique is that separating substrate (detail) from surface (overview) hides consequential detail from practitioners at gate moments. The Parnas episode suggests the critique may be wrong (information hiding improves software design when implemented correctly) but the implementation must be carefully designed so that the "information hidden" genuinely does not need to be seen routinely, and the interface for accessing it is clear when it does. CONFIDENCE: Historical case; directional implication. IMPLICATION: The substrate-and-surface separation is not inherently wrong, but the design of the surface must make it evident when hidden substrate detail is consequential. The failure mode is not the separation; it is the interface design that fails to signal when the hidden layer must be consulted.

**Finding 5.5 — AI-augmented documentation: drift amplification**

Recent analysis of AI-assisted development documentation (digital-streams.com, 2024; dev3lop.com, 2024) identifies AI-augmented development as an amplifier of the dual-maintenance problem: AI agents may update one layer without the other, or produce plausible-sounding summaries that diverge from the underlying detail. This is a new failure mode not present in pre-AI documentation literature. CONFIDENCE: Directional — practitioner analysis, no controlled studies. IMPLICATION: In RDD's context, where an AI agent generates or updates both substrate and surface, the risk of AI-driven divergence between layers is real. Mitigation is single-source derivation (agent generates surface from substrate, not independently).

### Q6: Documentation Read-Rate Decay Post-Handoff

**Finding 6.1 — Lethbridge, Singer, Forward (2003): "How Software Engineers Use Documentation: The State of the Practice"**

This IEEE Software empirical study used multiple data-gathering approaches across software practitioners to characterize documentation usage patterns. Key finding: software engineers do not update documentation as timely or completely as process personnel and managers advocate. Specification documents were the most frequently consulted; low-level design documents were among the least. The study confirms that documentation usage is strongly correlated with the current development task: documents are consulted during active development and consulted less (and updated less) after development concludes. The study characterizes documentation usage as task-triggered rather than continuous. CONFIDENCE: Empirically established (multi-site empirical study, IEEE Software publication). Direct applicability to decision-record documentation in methodology contexts is analogical but structurally consistent. IMPLICATION: Decision records (architectural, methodological) are structurally similar to low-level design documentation: detailed, decision-point-specific, not consulted outside the development context that produced them. The practitioner's observation ("no one reads them post-graduation") is consistent with this empirical finding.

**Finding 6.2 — Forward & Lethbridge (2002): The relevance of software documentation, tools and technologies**

This companion survey (48 practitioners) found that outdated documentation "can still be an effective resource" — contradicting the intuition that obsolescence disqualifies a document. The key finding is that the *type of question* being asked determines whether staleness matters: for understanding historical rationale, even outdated documents are useful; for operational guidance, staleness is disqualifying. CONFIDENCE: Empirically established (practitioner survey). IMPLICATION: For RDD's post-graduation use case, where the artifact trail serves agent context for future cycles, historical-rationale value is preserved even if the documentation is not actively maintained. This provides empirical support for the "good for agent context even if no one reads them" claim the practitioner makes.

**Finding 6.3 — Garousi & Garousi (2013, 2014): Usage and quality of technical software documentation**

These empirical studies at NovAtel (GPS software, 2013 EASE; 2014 Information and Software Technology) found that: (a) documentation usage for implementation is higher than for maintenance; (b) software design/architectural artifacts are most useful for implementation, while code comments are most useful for maintenance; (c) up-to-date information, accuracy, and precision are the highest-rated factors in documentation usefulness. The 2014 industrial case study confirmed that "in many projects, software documentation artifacts are outdated, incomplete and sometimes not beneficial." CONFIDENCE: Empirically established (industrial case study, peer-reviewed). IMPLICATION: Architectural and decision documentation is most useful during active development (building) and least consulted during maintenance — consistent with the practitioner's graduation-phase observation. For RDD, the implication is that ADR usefulness peaks during BUILD and DECIDE phases, then drops post-graduation. Agent context value may extend beyond this peak because agents can consume archival documentation without the re-orientation cost humans bear.

**Finding 6.4 — Brooks (1995): The Mythical Man-Month, onboarding and knowledge transfer**

Brooks identifies onboarding documentation as critical for knowledge transfer but observes that the cost of onboarding grows with corpus size and with time elapsed since decisions were made. Writing forces clarity at the time of writing, but the re-reading cost for a new team member is proportional to corpus depth, not to the significance of decisions. For RDD's graduation context: the ADR corpus that took cycles to build must be navigable by an agent (or new practitioner) in a single context window or traversal pass. Brooks's onboarding analysis supports the practitioner's felt experience that the corpus is "too much to grapple with as a person." CONFIDENCE: Established literature (foundational software engineering reference). Specific quantification of onboarding cost vs. corpus size is not provided. IMPLICATION: Corpus size is not neutral — there is a re-reading cost that grows with corpus depth. This provides theoretical grounding for the topology-compression goal (fewer, higher-level ADRs) as a contribution to onboarding quality, not just practitioner preference.

**Finding 6.5 — Gupta et al. (2026): Context Matters — Evaluating Context Strategies for Automated ADR Generation Using LLMs (arXiv:2604.03826)**

This study evaluates five context-selection strategies for LLM-based ADR generation across 750 open-source repositories. The key finding for this review: a **small recency window of 3–5 prior ADR records** provides the best balance between quality and efficiency. All-history context degrades quality relative to recency-windowed context. Retrieval-based context selection adds no statistically significant benefit in sequential ADR workflows. CONFIDENCE: Empirically established (peer-review pending; arXiv 2026, multi-repository evaluation). IMPLICATION: This directly addresses the corpus-size question for agent consumption. If a recency window of 3–5 records is optimal for LLM ADR generation, then flat all-corpus retrieval is suboptimal for agents as well as for humans. A structured substrate that supports recency-windowed and topologically-filtered retrieval would outperform flat corpus delivery. This is the strongest empirical finding bearing directly on how agents should consume an ADR corpus.

## Candidate Ranking (Plugin-Native-Weighted)

The following candidates are ranked on three criteria: (A) audit-substance preservation — does the candidate preserve decision rationale, rejected alternatives, and graduation triggers at the detail level? (B) multi-resolution viewability — does the candidate support overview-to-detail navigation without losing context? (C) plugin-native implementability — can the candidate be implemented with no MCP / external-database / graph-database dependency?

Scores: 1 (weak), 2 (partial), 3 (strong).

| Rank | Candidate | A: Audit | B: Multi-res | C: Plugin-native | Notes |
|------|-----------|----------|-------------|-----------------|-------|
| 1 | **JSON-LD with frontmatter navigation affordances** | 3 | 2 | 3 | W3C standard; typed edges; no external DB; human-readable in Markdown body; +29.6% retrieval gain (Volpini 2026). Navigation affordances (breadcrumbs, agent instructions) provide surface layer. |
| 2 | **YAML frontmatter virtual graph + structured body** | 2 | 2 | 3 | Lowest implementation cost; widely deployed pattern; implicit graph (no typed edges). Agent must infer topology. Sufficient for single-hop traversal; limited for multi-hop provenance queries. |
| 3 | **JSON linked-list (practitioner's candidate)** | 3 | 2 | 3 | Middle path: explicit typed links without full JSON-LD ontology overhead. No external dependencies. Design question: typed-link schema definition. No direct empirical evidence; analogically sound. |
| 4 | **Agent-emergent graph construction (GraphReader pattern)** | 2 | 3 | 3 | Best multi-resolution score (agent performs coarse-to-fine traversal). No structured authoring required. Inconsistent topology across sessions; provenance depends on agent inference quality. |
| 5 | **C4 model / arc42 hybrid (structured decomposition)** | 2 | 3 | 2 | Strong multi-resolution; established practice. Designed for structural decomposition, not decision rationale. Requires diagram tooling (Structurizr, Mermaid rendering). Partial plugin-native. |
| 6 | **Architecture Knowledge Graph / RDF / linked data** | 3 | 3 | 1 | Strongest audit-substance and multi-resolution; requires semantic wiki or RDF infrastructure. Not plugin-native. Enterprise-context deployment only. |
| 7 | **Spec-by-example / living documentation** | 3 | 1 | 2 | High audit-substance for behavior; no overview navigation. Rejected by practitioner for the same fine-grained-occlusion reason as scenarios-only. |

**Ranking rationale:** Candidates 1–3 are the viable plugin-native candidates for spike investigation. Candidates 4–7 are either infrastructure-heavy (6), multi-resolution-weak (7), or partially plugin-native (4, 5). The ranking weights plugin-native implementability highest because the public-facing plugin constraint is hard.

The difference between ranks 1 and 3 is primarily the typed-link schema question: JSON-LD provides a standard context mechanism for defining typed relationships (at the cost of JSON-LD authoring conventions); the JSON linked-list requires a custom schema design (which is simpler but proprietary). Rank 2 (YAML frontmatter) is the fastest starting point for a spike but has the weakest provenance semantics.

## Negative Cases Worth Highlighting

**1. Dual-maintenance staleness is not an edge case, it is the default outcome.** Every documentation system that attempts overview/detail separation without a single-source derivation mechanism will produce staleness drift. This is the primary failure mode of arc42, C4, and any two-layer ADR system that maintains the overview and detail independently. The mitigation is not "be more disciplined" — it is architectural: surface is computed from substrate, not independently maintained.

**2. Comprehensiveness is a trap.** Both arc42 and C4 fail in practice when they produce comprehensive but unread documentation. The failure mode is directly analogous to the practitioner's reported ADR-corpus overwhelm: more slots → more weight → less reading. The Calibration-with-Graduation-Trigger Pattern from Loop 1 is the RDD-specific mitigation, but it must survive operational test to be trusted.

**3. Zooming without context is worse than monolithic viewing.** Cockburn et al. (2008) documents empirically that zoom-based navigation generates extra cognitive load for linking pre-and post-zoom states. A substrate-and-surface architecture that implements "drill-in" (replace the overview with the detail) is likely worse than a flat document for practitioners who need to reason across levels simultaneously. The architecture must support focus+context (overview remains visible while detail is shown) rather than replace-context zoom.

**4. AI-driven layer divergence is a new failure mode.** In RDD's context, if the agent is generating or updating the corpus, it may update the substrate (add a new ADR record) without updating the surface (the overview). This creates an inconsistency that neither the practitioner nor a subsequent agent will notice until the surface is actively consulted. Single-source derivation is the only reliable mitigation, but it requires the derivation to run automatically on corpus change, not manually.

**5. Agent inference of graph topology is session-fragile.** The agent-emergent approach (Finding 4.3, GraphReader pattern) produces consistent results within a session but may produce different topology inferences across sessions or across different agent models. For a methodology corpus where provenance chains ("this ADR supersedes that one; this invariant is load-bearing for that decision") are consequential, session-fragile topology is a risk. This favors persisted structured substrate over purely emergent construction for RDD's specific use case.

**6. Small recency windows are optimal for agent consumption.** The Gupta et al. (2026) finding that 3–5 prior ADR records is the optimal context window for LLM-based ADR generation implies that flat all-corpus retrieval is suboptimal. A substrate that supports recency-windowed traversal and topologically-filtered retrieval should outperform flat delivery, even if the flat corpus fits in a context window. This is a counterintuitive finding: more context is not always better.

## Spike-Target Revision Recommendation

The watch-item from research-design-review-020.md asked: does Loop 2 evidence support the practitioner's JSON-linked-list / graph-substrate spike target, or does a different candidate warrant the spike?

The evidence partially supports the JSON-linked-list target but suggests a refinement. The strongest empirical evidence (Volpini et al. 2026, GraphReader 2024) points to two mechanisms that explain why structured substrates outperform flat text for agent navigation: (a) navigation affordances (breadcrumbs, explicit link chains, agent instructions) and (b) typed-edge provenance semantics (agents can follow "supersedes," "implements," "motivates" links without inferring them). The JSON linked-list candidate provides (a) but provides (b) only if the link schema includes typed edges.

The recommended spike target is therefore: **a plain-JSON structured record format with typed links** (not a full JSON-LD ontology, but more than an untyped linked list). Specifically, each record should carry: `id`, `type` (ADR / invariant / vocabulary term / scenario), `supersedes`, `implements`, `motivates`, `version`, and a `summary` field (the surface layer). This is the minimum typed-link schema needed to support multi-resolution navigation without external dependencies.

The spike should test whether (a) the summary field can be derived from the body content by an agent (single-source derivation), and (b) the typed links support the "overview → drill-in → detail" navigation the practitioner named. If the typed-link schema proves overly complex in practice, fallback to YAML frontmatter with explicit `supersedes` and `implements` fields is the next simplest option.

The spike does not need to reproduce the full Kantara or Architecture Knowledge Graph approach. A small-corpus prototype (Cycle 019's five ADRs + the Calibration Pattern) is sufficient to test the hypothesis.
