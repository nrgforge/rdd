**One internal tension worth surfacing to the practitioner.** ADR-100's §Scope, tier, and grounding states "**Tier: Skill-Structure Layer for the record**... This is anchored now" — language that reads as a present-tense claim (the mechanism *is* structurally anchored). But the same ADR's Supersession notes concede "the skill and orchestrator text that operationalize this ADR change... is deferred to BUILD." Per the orchestrator's own Three-Tier Enforcement Classification (`skills/rdd/SKILL.md:319-338`), Skill-Structure Layer anchoring specifically means "a concrete workflow step in a named skill" — and no such step exists yet in any skill file (confirmed above). So the tier claim and the deferred sweep are in tension: as written today, the triage-record mechanism is not yet Skill-Structure-anchored by the methodology's own definition of that term; it is a documented intention operating informally in the last two gate notes. This doesn't require a code fix — it's a phrasing question for the ADR itself (ADR-099 uses the more careful "Skill-Structure Layer anchoring is the graduation target" pattern for the analogous case; ADR-100 could match that pattern, or the practitioner may prefer to keep the stronger claim and treat the BUILD sweep as merely completing an already-committed tier rather than establishing it). Surfacing this as a pivot candidate for BUILD entry, not auto-resolving it.

**The 78-ADR status debt is much larger than the task's named instances.** The task named ADR-058 and ADR-061 as the minimum; the actual count across the corpus is 78 ADRs (roughly 85% of ADR-001 through ADR-091). This isn't a Cycle 020 problem — it's a standing artifact of the methodology never having run a corpus-wide status reconciliation pass — but it's large enough that `/rdd-conform` should probably treat it as its own work item rather than a footnote, since 78 rows in one conformance table would otherwise swamp the two ADRs this scan was actually scoped to check.
