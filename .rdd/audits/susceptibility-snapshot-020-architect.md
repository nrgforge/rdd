## Interpretation

Three phases of declining practitioner engagement (metaphor at DISCOVER → "those are all reasonable terms" at MODEL → "C" at DECIDE) are followed by a phase with no engagement to measure yet, because the gate is still pending. That absence is not itself new evidence for fatigue — but the *mechanism* that produced ARCHITECT's content in that absence is new evidence, and it does not point toward "design working."

The load-bearing move this phase makes is procedural, not architectural: ARCHITECT ran entirely on an inherited driving-mode default, per an instruction written by a different session's agent, on the authority of an ADR that misdescribes its own founding moment. ADR-100 §Posture says the driving/building choice for this reflexive cycle was "put to the practitioner at the Cycle 020 DECIDE gate for confirmation" — using the word "pivot." It was not. The DECIDE gate's actual presentation (documented independently by the decide-boundary snapshot and corroborated here against the same source) bundled "driving mode continues" into a two-item list of unobjected defaults, alongside "two ADRs, not one or three." A default not objected to and a pivot ruled on are exactly the distinction ADR-100 rule 2 itself exists to keep visible ("route-level choices are presented as overridable defaults... a Pivot Point... changes the destination"). ADR-100 fails its own test describing itself, and ARCHITECT's gate note — written after ADR-100 — repeats the more accurate framing ("the DECIDE-gate default, not overridden") one document away from the ADR that gets it wrong. Nobody caught the discrepancy between the two documents before this snapshot, because nobody was positioned to: the ADR was drafted and the gate note was drafted by the same orchestrator context, in the same phase, under the same unexamined premise.

This is the third and fourth data point (following MODEL's and DECIDE's) of the same underlying failure mode: a claim of practitioner confirmation that the source transcript does not support, made inside the very mechanism (ADR-100) built to prevent exactly that. It is evidence for the harm-evidence branch of ADR-100's own graduation trigger, which already counts three such instances from this cycle "predating the rules' formal adoption." This would be a fourth, postdating adoption — inside the ADR that adopted the rule, about its own operation.

The Glossary-coverage miscount is smaller in stakes but instructive in kind: a "Resolved (engine)" disposition is, by ADR-100's rule 2, supposed to be the category the practitioner never has to check — engine detail, logged and correct. When an engine-level self-check contains a specific, falsifiable count and the count is wrong, the entire premise of "engine-level, safe to resolve silently" weakens, because the category's reliability rests on the resolver's accuracy, and this snapshot found the resolver wrong on the first row checked in depth. This is not evidence the whole table is unreliable — most rows (retrofit fixes, hook wiring, release target) are checkable, mundane, and correct — but it is evidence that "Resolved (engine)" status was not independently verified before being written down, which is the same gap the DECIDE snapshot found in "Resolved and surfaced" dispositions one phase earlier.

Set against this, the Inversion Principle check that ARCHITECT did run (Substrate behind, Surface Views in front, because the practitioner's own phrase was "a graph behind a human-friendly format," not because it was easier to implement) is genuine and well-reasoned — a real fork was named (developer convenience: co-located directories; user model: front/behind) and resolved toward the user's model, with the reasoning shown. That check is not pro forma. But it was run once, on the most visible boundary, and not run on the second boundary this phase creates: domain-model.md, the practitioner's primary hand-maintained reference, gaining an agent-owned marked region. Whether that specific hybrid-ownership choice tracks the practitioner's mental model of "what's mine to edit" was never tested against an alternative the way Substrate-vs-Surface was — it was settled on tooling-drift-avoidance grounds only. The module-ownership concentration in Orchestrator (14 of 32 Cycle 020 responsibility-matrix rows, on independent count) points the same direction: work keeps landing in the module that is easiest to extend from within an existing prompt, which is a developer-convenience gravity the Inversion Principle check is specifically designed to counteract, and did counteract once, not twice.

## Triage evaluation

**(1) Were pivots correctly identified?** Partially. The one pivot ARCHITECT selected (which corpus read validates the cycle at the BUILD gate — ADR overview vs. product-discovery) is a genuine destination-level question, developed with real belief-mapping on both sides, and is correctly a pivot under the stated criterion ("changes what gets built, for whom, or why" — which reading the practitioner is handed changes what "done" looks like at the next gate). But it is not the only candidate that criterion could apply to. The driving/building posture for the rest of this reflexive cycle changes *how* every subsequent finding this cycle reaches the practitioner — arguably closer to "why" (the practitioner's own DISCOVER-gate rationale was about what they, personally, need to rule on) than a route detail. It was filed as a settled default via ADR-100's overclaimed history rather than surfaced as this gate's second candidate pivot or even named as a live option. The agent's gloss on Invariant 0's list ("what gets built, for whom, or why") matches Invariant 0's actual text reasonably faithfully as a phrase, but its *application* here — routing a question about the practitioner's own engagement mode into "default" rather than "pivot" — is the weak point, not the wording.

**(2) Were framing-class findings surfaced rather than silently resolved?** No framing-audit ran this phase (ARCHITECT does not dispatch one; correctly absent from the gate note). The relevant framing-class item this snapshot surfaces — that ADR-100's own posture claim doesn't match its cited transcript — was not caught by ARCHITECT's own process at all; it surfaces here because this snapshot re-derived it from source rather than trusting the inherited premise. It was not "resolved" by ARCHITECT so much as never examined.

**(3) Did any resolve disposition hide a destination change?** Not a destination change in the sense of covertly altering scope. But the Glossary-coverage row ("Resolved (engine)... Orchestrator owns eleven rows (threshold twelve)") hides a *miscount* behind a Resolved label, and the inherited driving-mode default hides an *unconfirmed posture choice* behind a "not overridden" framing that presupposes the practitioner had a clear, isolated chance to override it. Neither is a hidden destination change. Both are instances of the same category ADR-100 exists to prevent: content selection presented with more settledness than the record supports.

## Recommendation

**Grounding Reframe recommended.**

**What is uncertain:**
1. Whether "driving mode" is actually the practitioner's considered choice for the remainder of this specific reflexive, self-referential cycle, or an inherited default whose legitimating claim (ADR-100 §Posture: "put... as a pivot" at DECIDE) does not match the DECIDE transcript.
2. Whether the Glossary-coverage "Resolved (engine)" disposition's specific claim (Orchestrator owns eleven rows against a threshold of twelve) is accurate — independent count here says fourteen, past the stated threshold, and the threshold itself has no corpus provenance.
3. Whether the domain-model.md marked-region decision (agent-generated text inside the practitioner's hand-maintained constitutional artifact) would survive the same product-facing Inversion Principle test that Substrate-vs-Surface Views received, given it was settled on tooling grounds alone.
4. Whether Orchestrator's module-ownership concentration in the Cycle 020 responsibility matrix reflects a boundary that serves the practitioner's mental model or one that serves the path of least implementation resistance inside an already-large module.

**Concrete grounding actions:**
- At the ARCHITECT gate, ask the driving/building posture question on its own, not folded into anything else: "ADR-100 says this was settled as a pivot at DECIDE; the DECIDE transcript shows it as an unobjected default. Given three snapshots have now found concrete problems specifically when this reflexive cycle ran in reduced-visibility mode, do you want the rest of Cycle 020 — starting with this gate — to run driving, or to declare the reflexive building opt-in ADR-100 §Posture already makes available?"
- Before treating Glossary coverage as settled, recount Orchestrator's rows in the Cycle 020 responsibility matrix and correct the gate note's figure, or show the practitioner the discrepancy directly if a recount is deferred to BUILD.
- Ask the practitioner one direct question about domain-model.md: "Cycle 020 gives one region of your domain model to a tool. Are you comfortable with that specific file carrying both hand-maintained and generated rows, or would you rather the generated content live only in `docs/views/` and domain-model.md stay entirely yours?"
- Correct ADR-100 §Posture's own text (the "put... as a pivot" line) to match what the DECIDE gate note actually shows, so the next reader of ADR-100 does not inherit the same overclaim ARCHITECT just did.

**What the practitioner would be building on without grounding:** BUILD would execute WP-A through WP-J against a system design whose operating posture for the rest of this reflexive cycle was never actually chosen in an isolated, answerable moment — inherited instead through a chain (resumption bookmark → ADR-100's self-description → ARCHITECT's "not overridden" default) in which each link cites the one before it as settled. It would also inherit a "Resolved (engine)" self-audit with at least one checkable factual error, on a phase whose whole premise is that engine-level resolutions don't need practitioner verification because the agent got them right.
